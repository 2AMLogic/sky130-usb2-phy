## The 18 failing rows and their attribution

The failing rows reduce to one extracted-side number: `RDM_t0` = 1993.5 ohm / `RDP_t0` = 1993.2 ohm in series with each pad (vol 2.13 V = the 1.5 k ohm pull-up against that lead; rout = 0.3 V / I through it). `sim/diff-driver-pex/attribution_walk.py` (committed; its output is stored as `attribution-walk.txt`) reproduces the extractor's number to 0.03 ohm **from the GDS geometry alone** and attributes it per fragment:

| layer fragment (per pad) | area | squares charged | resistance |
|---|---|---|---|
| poly head (0.8 x 20 um bar, current crosses its 0.8 um neck) | 16.0 um2 | 25.00 | 1205.0 ohm |
| li1 head (0.33 x 20 um bar, same crossing) | 6.52 um2 | 59.91 | 766.8 ohm |
| met1 pad + met2 drop (~36 um) + met3 stub | 18.8 um2 | 174.1 | 21.6 ohm |
| **total** | | | **1993.2-1993.5 ohm** |

The two head fragments are 97% of the total. The parasitics kernel's equivalent-rectangle square count (squares = L/W >= 1 per fragment) charges each head as if current flowed along its 20 um length; the pad current actually crosses the 0.8 um / 0.33 um neck (~0.04 squares, about 2 ohm). The drawn-metal path is ~20-30 ohm. The kernel's own docstring covers non-convex over-counting as "conservatively high"; this is a different failure -- a convex fragment with the direction assumption inverted -- filed as 2AMLogic/klayout-tools#7028. The tool's own remedy route cannot take over: `--resistance-graph` falls back to the same legacy scalar for these nets (`via_resistance_unknown`: the sky130 deck publishes no licon cut resistance), and `--resistance-graph-r-cut 0` still falls back (`graph_status_skipped`) -- probes stored as `probe-resistance-graph.json` / `probe-resistance-graph-rcut0.json`, filed as 2AMLogic/klayout-tools#7029. For the same reason a layout iteration cannot fix these rows: the head geometry is intrinsic to the res_generic_po device family's drawing style (a contacted head on a 20 um-wide device), so the rows are parked on the upstream issues, not on the layout.
